# Harness

계획 → 적대적 비판 → 사용자 승인 → 구현 → 독립 리뷰.
`/setup` 전에도 기본 모드로 동작하고, 설정 후에는 `.claude/harness.json`의 프로필과 검사 명령이 더해진다.

**응답 언어:** 사용자에게 보내는 모든 응답(서브에이전트 결과를 옮기거나 요약할 때 포함)은 사용자가 대화에서 쓰는 언어로 쓴다. 한국어로 시작한 대화는 한국어로, 영어로 시작한 대화는 영어로 이어간다. 첫 문장부터 지킨다.
<!-- 유래: v0.1 도그푸딩 — 한국어 대화인데 최종 응답 첫 문장이 영어였다. 언어 조항이 서브에이전트에만 있었다 -->

```
요청
  ↓
[0] 작업 분류, 영향받는 패키지 → 활성 프로필, 트랙 판정
  ↓ 표준 트랙                        ↓ 경량 트랙
[planner] PLAN_OUTPUT                [오케스트레이터] 짧은 플랜
  ↓                                   │
[plan-critic] CRITIC_OUTPUT           │
  ↓ 오케스트레이터가 플랜 보강        │
  └──────────────┬────────────────────┘
                 ↓
         플랜 제시 → 사용자 승인
                 ↓
[developer] DEVELOPER_OUTPUT
                 ↓
[reviewer] REVIEW_OUTPUT ── 수정 필요 → developer (최대 3회)
                 ↓
         최종 보고 → 커밋 승인 대기
```

## 산출물 (`_workspace/`, gitignore됨)

서브에이전트 출력은 대화가 요약되면 사라진다. 그래서 산출물을 파일로 남긴다.
**각 파일은 작성자의 원문 그대로다.** 서브에이전트는 호출 때 넘겨받은 경로에 원문을 직접 쓰고, 오케스트레이터에게는 경로와 짧은 요약만 반환한다.

- 오케스트레이터는 서브에이전트 산출물을 다시 쓰거나 요약해서 저장하지 않는다. 이유: 재개·감사가 불가능해지고, 다음 에이전트가 손실된 플랜을 받는다.
- 오케스트레이터의 보강(critic 반영, 승인 코멘트)은 원문을 덮어쓰지 않고 파일 끝의 `## 보강` / `## 승인 코멘트` 섹션에 덧붙인다.
- 다음 에이전트에게는 요약이 아니라 파일 경로를 넘기고 원문을 읽게 한다.
- planner, plan-critic, reviewer가 `_workspace/` 밖에 쓰면 guard 훅이 막는다.
<!-- 유래: v0.1 도그푸딩 — 오케스트레이터가 planner 원문(B1~B5, F1~F5)을 한 줄씩으로 압축해 저장했고, reviewer의 체크리스트 판정은 파일에 남지 않았다 -->

| 파일 | 작성자 | 내용 |
|---|---|---|
| `state.md` | 오케스트레이터 | 현재 단계, 작업 유형, 트랙, 영향받는 패키지·프로필, 리뷰 라운드 |
| `00_input.md` | 오케스트레이터 | 요청 원문, 작업 유형과 판정 이유, 미결 질문 |
| `01_plan.md` | planner (경량: 오케스트레이터) | PLAN_OUTPUT 원문 + `## 보강` |
| `02_critic_round{N}.md` | plan-critic | CRITIC_OUTPUT 원문 |
| `03_approved_plan.md` | 오케스트레이터 | `01_plan.md`를 `cp`로 복사한 뒤 `## 승인 코멘트`를 덧붙임 |
| `04_developer_round{N}.md` | developer | DEVELOPER_OUTPUT 원문 |
| `05_review_round{N}.md` | reviewer | REVIEW_OUTPUT 원문 |
| `06_final_report.md` | 오케스트레이터 | 최종 보고 |
| `checks_last.txt` | Stop 훅 | 마지막으로 실행된 검사 결과 (통과 / 실패) |

**재개:** `_workspace/state.md`가 있고 요청이 그 작업의 후속이면 그 단계부터 이어간다.
다른 작업이면 폴더를 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮기고 처음부터 시작한다. 애매하면 묻는다.

## 0. 분류

- 작업 유형: `기능` | `버그` | `리팩터링` | `성능` | `핫픽스`. 여러 개에 걸치면 가장 위험한 것을 고른다 (버그 > 기능 > 성능 > 리팩터링).
- 영향받는 패키지: 변경이 닿을 경로를 `.claude/harness.json`의 `packages[].path`와 맞춘다 (가장 길게 일치하는 경로 우선).
  그 패키지의 `profiles`가 활성 프로필이다. 프로필이 없으면 기본 모드이며, 이 사실을 한 번 알린다.
- 트랙: `.claude/templates/plan.md` 1번 표와 활성 프로필의 추가 트랙 기준을 직접 채운다. 모두 "아니오"일 때만 경량이다. 확신이 없으면 표준으로 둔다.
- 계획을 막는 모호함은 계획 전에 묻는다. 막지 않는 것은 미결 질문으로 넘긴다.
- `00_input.md`와 `state.md`를 쓴다.

## 1. 플랜

**표준 트랙:** `planner` 에이전트를 호출한다: 요청 원문, 작업 유형, 영향받는 패키지와 활성 프로필, 미결 질문, 0단계의 트랙 판정표, 산출물 경로 `_workspace/01_plan.md`.
planner가 트랙을 경량으로 뒤집어도 표준 트랙으로 진행한다.

**경량 트랙:** planner를 호출하지 않는다. 오케스트레이터가 템플릿의 0(탐색 요약)·1(트랙 표)·2(요구사항)·4(단계)·6(테스트)번만 채운 짧은 플랜을 `01_plan.md`에 쓴다.
쓰는 중에 1번 표나 프로필 기준에 "예"가 하나라도 생기면 표준 트랙으로 바꿔 planner를 호출한다.
<!-- 유래: v0.1 도그푸딩 — 금액 표기 한 줄 변경에 planner·developer·reviewer 3회 호출과 승인 왕복이 필요했다 -->

## 2. plan-critic (표준 트랙만)

`01_plan.md` 경로, 요청, 활성 프로필, 산출물 경로 `_workspace/02_critic_round1.md`를 넘겨 `plan-critic`을 호출한다.
Critical과 Major 지적은 오케스트레이터가 `01_plan.md`의 `## 보강`에 반영한다. 비판이 플랜의 전제 자체를 무너뜨릴 때만 planner를 다시 호출한다.

핫픽스는 **사용자가 긴급하다고 명시한 경우에만** 이 단계를 건너뛸 수 있다. 그때는 승인 요청에 그 사실을 밝히고,
배포 후 표준 트랙 검토를 권한다.

## 3. 사용자 승인

제시할 것: 플랜(간결하게), 비판 지적과 각각의 반영 방법, 트랙, 남은 미결 사항.
승인 요청의 끝에는 아래 두 블록을 항상 이 형식으로 붙인다. 해당이 없으면 "없음"이라고 쓴다.

```
### 비판 지적 → 반영
| # | 심각도 | 지적 | 반영 방법 (반영함: 플랜의 어디 / 반영 안 함: 이유) |

### 승인 전에 정해 주세요
1. {결정할 것} — 권고: {안과 이유} / 대안: {안}
```

플랜의 `[기존 결함]` 항목(건드린 화면·경로의 기존 결함을 범위 밖으로 둔 것)은 모두 "승인 전에 정해 주세요"에 올린다.

명시적 승인을 기다린다. "좋아", "진행해", "승인" 같은 말은 승인이다. 침묵과 질문은 승인이 아니다.
`01_plan.md`를 `03_approved_plan.md`로 복사하고, 끝에 `## 승인 코멘트`(사용자의 결정과 코멘트)를 덧붙인다.
<!-- 유래: v0.1 도그푸딩 — 두 블록이 모델 재량으로만 나와서 품질이 매번 달랐다 -->

## 4. developer

`03_approved_plan.md` 경로, 작업 유형, 영향받는 패키지, 산출물 경로 `_workspace/04_developer_round{N}.md`를 넘겨 `developer`를 호출한다.
플랜 결함을 보고하면 멈추고 사용자에게 가져간다.

## 5. reviewer

`03_approved_plan.md`와 `04_developer_round{N}.md` 경로, 활성 프로필, 트랙, 산출물 경로 `_workspace/05_review_round{N}.md`를 넘겨 `reviewer`를 호출한다.
"수정 필요: 예"면 지적을 넘겨 `developer`를 다시 호출한다. 최대 3회, 그 뒤엔 멈추고 사용자에게 보고한다.

## 6. 최종 보고

정리할 것: 무엇이 바뀌었나, 리뷰 결과, 미룬 것, 그리고 **마지막 검사 결과(필수)**:
- 이번 턴에 reviewer가 실행한 검사와 결과(통과 / 실패 + 요약). 근거 없이 "통과"라고 쓰지 않는다.
- `_workspace/checks_last.txt`가 "결과: 실패"면 그 요약도 적는다. 이 파일은 Stop 훅이 쓰며, 훅은 이 보고 **뒤에** 실행된다.
- 프로필 체크리스트의 **미검증** 항목(예: 화면을 렌더하지 못함)을 모두 적는다.
<!-- 유래: v0.1 도그푸딩 — Stop 훅이 두 번째 종료를 무조건 통과시켜, 검사 실패 사실이 보고에서 사라질 수 있었다 -->

`06_final_report.md`에 저장한다.
진행 중 하네스가 잡았어야 할 문제가 있었다면 교훈 기록(`docs/lessons/`)을 제안한다.
커밋은 승인을 기다린다.
