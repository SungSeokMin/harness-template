# PLAN 템플릿

`planner` 에이전트가 반환하는 `PLAN_OUTPUT`의 구조입니다.
0~7번은 공통 섹션입니다. 8번은 활성 프로필마다 `.claude/profiles/<profile>/plan.md`에서 붙입니다.

---

## 0. 탐색 요약

실제로 읽은 것만 적는다. 확인하지 않은 내용은 적지 않는다.

- 읽은 파일, 실행한 검색
- 바꾸려는 코드의 현재 동작
- 이 변경이 따라야 할 기존 패턴

## 1. 트랙

아래 기준이 **모두 "아니오"일 때만 경량(light)**, 하나라도 "예"면 **표준(standard)**. 답마다 근거를 한 줄 남긴다.

| 기준 | 예/아니오 | 근거 |
|---|---|---|
| 공개 계약(API 형태, props, CLI 플래그, 파일 형식)이 바뀌는가? | | |
| 저장된 데이터나 그 스키마가 바뀌는가? | | |
| 인증·권한·결제·개인정보를 건드리는가? | | |
| 기존 동작의 의미가 바뀌는가? (결과가 달라지는 버그 수정 포함) | | |
| 둘 이상의 패키지나 레이어에 걸치는가? | | |

활성 프로필이 자기 기준을 추가한다 (8번 참고).

**트랙: 경량 | 표준**

## 2. 요구사항

- 작업 유형: 기능 | 버그 | 리팩터링 | 성능 | 핫픽스
- 목표 (사용자 요청 원문)
- **하지 않을 것** — 이 변경이 하지 않는 일
  - 건드린 화면·경로의 기존 결함(프로필이 요구하지만 원래 없던 것)을 고치지 않고 두면 `[기존 결함]`으로 표시한다. 표시 없이 범위 밖으로 두지 않는다.
    이유: 프로필 요구와 최소 변경이 충돌할 때 판단은 사용자가 한다. 오케스트레이터가 승인 요청의 "승인 전에 정해 주세요"로 올린다.
    <!-- 유래: v0.1 도그푸딩 — 로딩·빈·에러 상태가 없던 화면을 기준 없이 "기존 결함, 범위 밖"으로 통과시켰다 -->
- 가정과 차단하지 않는 미결 질문

## 3. 제약

모든 행은 확인 가능해야 한다.

| 구분 | 제약 | 확인 방법 | 확인 주체 |
|---|---|---|---|
| Must | {예: 기존 응답 형태 유지} | {테스트 / 명령 / 리뷰} | {테스트, 훅, reviewer} |
| Must not | {예: 새 의존성 추가 금지} | | |

## 5. 실패 시나리오

| 시나리오 | 기대 동작 |
|---|---|
| | |

## 6. 테스트

- 정상 경로
- 경계값과 잘못된 입력
- 5번의 실패 시나리오 각각
- 버그: 수정 **전에** 버그를 재현하는 테스트

## 7. 작업 유형별 섹션

| 유형 | 필수 |
|---|---|
| 기능 | 수용 기준: 사용자 관점의 완료 조건을 관찰 가능한 형태로 (예: `GET /orders?status=PAID` → PAID 주문만 반환) |
| 버그 | 근본 원인, 재현 경로, 같은 패턴이 있는 다른 위치 |
| 리팩터링 | 동작 보존 계약(무엇이 그대로여야 하나)과 변경 범위 경계 |
| 성능 | 기준 측정값, 목표, 측정 방법 |
| 핫픽스 | 롤백 방법 |
