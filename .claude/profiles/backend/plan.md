# backend 프로필 — 플랜 섹션

## 추가 트랙 기준 ("예"가 하나라도 있으면 표준)

| 기준 | 예/아니오 | 근거 |
|---|---|---|
| 상태값을 추가하거나 전이 규칙을 바꾸는가? | | |
| 여러 쓰기가 함께 성공하거나 함께 실패해야 하는가? | | |
| 동시에 두 번 호출되거나 재시도될 수 있는 쓰기 경로를 추가하는가? | | |
| 외부 사이드 이펙트(알림, 결제, 메시지, 잔액)를 호출하는가? | | |

## B1. 상태 전이

| 시작 상태 | 이벤트 | 종료 상태 | 조건 | 위반 시 에러 |
|---|---|---|---|---|

- 금지 전이와, 코드의 **어디서** 막는지
- 이 상태를 읽는 기존 코드(배치, 조회, 집계, 알림)와 각각의 영향 여부

## B2. 원자성

- 함께 커밋돼야 하는 쓰기와 트랜잭션 경계
- 트랜잭션 밖의 사이드 이펙트(알림, 외부 API): 커밋 후 실행, 실패하면 어떻게 되나

## B3. 멱등성과 동시성

- 같은 요청이 두 번 오거나, 두 요청이 경쟁하면 어떻게 되나
- 첫 요청은 성공했는데 응답이 유실되어 클라이언트가 재시도하면 무엇을 받나 (상태 코드, 본문)
  <!-- 유래: v0.1 도그푸딩 — 취소 기능에서 재시도한 클라이언트가 400을 받는 문제를 아무도 짚지 않았다 -->
- 막는 방법: 유니크 제약, 조건부 업데이트, 락, 멱등성 키

## B4. 권한

- 누가 호출할 수 있고, 소유권을 어떻게 확인하나

## B5. 입력 검증

- 모든 입력 필드: 타입, 범위, 필수 여부, 반환하는 에러
